# Operational Guide

This document describes the recurring operational procedures used to develop and maintain the TaskFlow project.

Its purpose is to ensure that contributors follow consistent operational practices throughout the project's lifecycle.

---

# OPS-0001

## Title

Start Project Development

## Objective

Prepare a contributor to begin working on the project.

## Prerequisites

* Access to the project repository
* Development environment configured
* Required project dependencies available

## Procedure

1. Obtain the latest version of the project.
2. Prepare the development environment.
3. Verify that the project starts successfully.
4. Review the current Project Context before making changes.

## Expected Result

The contributor is ready to begin development with an up-to-date understanding of the project.

## Notes

Always review the Decision Log and Open Work documents before starting new work.

---

# OPS-0002

## Title

Implement a New Feature

## Objective

Introduce a new feature while preserving Project Continuity.

## Prerequisites

* Approved feature requirements
* Understanding of the existing architecture

## Procedure

1. Review related Project Context documents.
2. Implement the feature.
3. Update the Architecture document if structural changes were introduced.
4. Record significant decisions in the Decision Log.
5. Update Knowledge if durable information has changed.
6. Update Open Work to reflect completed or newly identified tasks.

## Expected Result

The feature is implemented and the Project Context remains consistent with the source code.

## Notes

Project Context should evolve together with the project, not after it.

---

# OPS-0003

## Title

Prepare a Release

## Objective

Prepare a stable version of the project for publication.

## Prerequisites

* Planned work completed
* Outstanding critical issues resolved

## Procedure

1. Verify that planned work is complete.
2. Review the Project Context for accuracy.
3. Confirm that documentation reflects the current state of the project.
4. Publish the release according to the project's release process.

## Expected Result

A stable release accompanied by an up-to-date Project Context.

## Notes

A release is considered complete only when both the software and its Project Context accurately represent the current state of the project.
